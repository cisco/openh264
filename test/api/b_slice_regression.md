# Synthetic B-slice reference regression

`b_slice_regression.py` is an optional developer regression for the three
B-slice correctness changes in `rec_mb.cpp`, `deblocking.cpp`, and
`parse_mb_syn_cavlc.cpp`. It creates every input from FFmpeg's `testsrc2`; it
contains no camera footage, downloaded test vectors, or proprietary assets.
The script is BSD-2-Clause. The generated test patterns may be freely
redistributed. FFmpeg/libx264 are developer tools only and are not added as
OpenH264 build or runtime dependencies.

Build the native console, then run:

```sh
make -j2 USE_ASM=No BUILDTYPE=Release h264dec
python3 test/api/b_slice_regression.py --decoder ./h264dec --output /tmp/b-slice-scalar
make clean
make -j2 USE_ASM=Yes BUILDTYPE=Release h264dec
python3 test/api/b_slice_regression.py --decoder ./h264dec --output /tmp/b-slice-simd
```

Python 3 and FFmpeg with libx264 are required. `--ffmpeg` selects a particular
executable; `--cases` selects individual cases. Every output directory must be
new. Each case has exactly 40 320x240 frames. The native console disables error
concealment and uses its default single-threaded path. Both `DecodeFrameNoDelay`
and legacy `DecodeFrame2` console paths drain pending pictures at EOS. The test
requires every Y/U/V byte and the complete output length to match FFmpeg's
reference decode, with no tolerance relaxation. Logs, encoder parameters,
executable/version identifiers, media hashes, and `report.json` are retained.
FFmpeg/libx264 versions can change generated bytes, so each run records the
reference actually generated instead of assuming cross-version hash stability.

The in-tree `DecoderPrediction.Bi4x4TemporaryLumaUsesSubpartitionOffset` test
constructs a single macroblock with all four enclosing 8x8 regions subdivided
into bi-predicted 4x4 blocks. It tests scalar and available native MC functions,
checks every main/temporary luma/chroma pixel and surrounding canaries, and
needs no external codec. This covers the 4x4 temporary-destination error even
when an encoder does not select that subpartition shape. Removing only the
`rec_mb.cpp` fix makes this regression fail.

## Observed before/after

Fresh upstream `1a0073f0322c8b74cbcb75ca1bb1c3d19d75538d`, macOS arm64,
FFmpeg 7.1 with libx264, release scalar build, both API modes:

| Synthetic case | Master max Y/U/V error | With all three fixes |
| --- | ---: | ---: |
| Spatial CABAC | 3 | 0 |
| Spatial CAVLC, 4x4 transforms | 3 | 0 |
| Temporal CABAC, 4x4 transforms | 3 | 0 |
| Temporal CAVLC, 4x4 transforms | 207 | 0 |
| Unweighted spatial CABAC | 3 | 0 |
| Deblocking-disabled spatial CABAC control | 0 | 0 |
| P-frame control | 0 | 0 |

The patched AArch64 NEON release build also produced all 40 frames bit-exact
for all seven cases in both API modes. The direct 4x4 regression passes with
scalar/native MC and fails when only its source correction is removed.

Earlier Linux amd64 scalar/SSE/AVX2 checks of OpenH264 2.6.0 plus the exact
merged #4004 backport and these corrections were also bit-exact for the
retained spatial and temporal-CAVLC synthetic streams in both API modes.
Those are supporting results on the older source, not a claim that current
master was rebuilt or its full suite run on Linux. This regression does not
establish complete H.264 conformance or multi-threaded-decoder correctness.
CAVLC with 8x8 transforms is outside the tested capability; CAVLC cases
explicitly use 4x4 transforms. No existing test-vector expected hashes are
changed by this patch.
